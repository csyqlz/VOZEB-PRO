# 电商商品图生成 SOP 规格

## 目标

为跨境电商家居商品提供一句话图生图体验：用户上传或引用目标图片，可选添加辅助参考，再用一句自然语言描述希望得到的结果。系统分别观察图片内容和解析本轮用途，完成视觉分析、编辑规划、模型路由和生成，技术检查通过后立即交付图片。视觉质检默认关闭；管理员开启后由既有 Worker 在交付后提供参考建议，不撤回结果。

首个 MVP 固定为：

```text
单张白底商品图 → 单张欧美家居生活方式场景图
```

首期同时支持同一对话中的连续编辑，但不开放商品颜色、材质和结构修改。

## 范围

### 首期包含

- `/create` 统一创作入口。
- 一张商品主参考图。
- 可选一张场景参考图。
- 一句自然语言创作请求。
- `product_to_scene` 商品场景生成。
- `local_edit` 的背景、环境、场景道具、光线和阴影修改。
- `scene_edit`：上传完整场景图后局部修改，允许没有独立商品锚点；柜体等主体的保护约束仍贯穿规划和执行。
- 连续编辑：默认继承最近成功结果，支持明确引用历史结果建立编辑分支。
- 原始商品锚点与当前场景基线双基线。
- `strict_product` 商品严格保真策略。
- GPT-5.6、gpt-image-2.5 和 nano banana 2 的逻辑角色路由。
- 生成后的技术交付检查、可选视觉建议与灰度回退。

### 首期不包含

- Canvas 和短剧入口。
- 多商品组合。
- 海报文字重排。
- 商品颜色、材质、结构或包装文字修改。
- 自动多轮修复。
- 用户手工配置模型、策略、mask 或内部提示词。
- 计费规则改造。

## 用户 SOP

1. 用户上传或引用一张目标图片；商品场景生成使用可靠商品图。
2. 用户可选添加风格、光线或构图参考图。
3. 用户输入一句话，例如“参考 A 的光线，修改 B”。
4. 系统分别记录可见内容与本轮用途；A 提供可靠光线线索，B 作为目标。只有事实充分且用途确有歧义时，才请用户确认一次。
5. 系统识别用户意图并生成内部 `EcommerceEditPlan`。
6. 系统以 `strict_product` 生成结果，保护商品核心区并允许背景和融合光晕区生成。
7. 系统检查真实媒体、尺寸、蒙版保护和保存结果；通过后登记资产并完成任务。
8. 用户看到一张结果图和简短状态，不看到内部计划、提示词或模型选择。
9. 用户可以继续输入“再亮一点”“把右边的绿植去掉”等一句话，默认基于最近结果继续编辑。

视觉质检默认不调用模型；开启时在已交付结果后补充建议，用户无需等其完成才能下载、引用或继续编辑。报告失败、不可用或与分析结论矛盾都不把任务退回。后台报告在刷新或重新打开历史时读取，完成事件流不因质检继续占用发送状态。

用户明确改用新的商品目标时，系统建立对应的商品锚点；新增辅助参考不自动替换当前目标或锚点。用户明确引用历史结果时，系统从该结果创建新的编辑分支，不覆盖原结果。

## 领域模型

领域词汇以[仓库的 CONTEXT.md](../../../CONTEXT.md) 为准。初始方案的词汇及契约保留为历史来源，当前增量须区分以下概念：

- 目标图片：本轮实际要修改的图片，与图内待编辑对象或区域分别记录。
- 图片内容事实：实际可观察内容、完整性、原始置信度和证据。
- 参考用途：编辑目标、商品身份、风格、光线和构图；同图可承担多个用途。
- 可靠线索：有实际证据支持的局部风格、光线、构图或材质外观信息。

- 商品主参考图：提供商品身份与受保护事实，来源于明确目标或既有商品锚点。
- 场景参考图：提供获准环境、风格、光线或构图线索，不能替代商品事实。
- 原始商品锚点：连续编辑链路中永久的商品事实来源。
- 当前场景基线：最近成功结果，用于继承当前场景和已完成的环境变化。
- 商品核心区：轮廓、Logo、包装文字、颜色、比例、材质纹理和主体像素。
- 融合光晕区：边缘、接触阴影、反射、高光和少量环境遮挡的有限区域。
- 场景增量：本轮新增或改变的背景、道具、光线、氛围和构图内容。
- 编辑分支：从明确选中的历史结果创建的新连续编辑链路。

## 核心契约：EcommerceEditPlan

`EcommerceEditPlan` 是用户自然语言、视觉理解、模型路由、图片执行和结果验收之间的唯一内部任务契约。用户原话、图片事实、本轮用途、内部计划和最终执行 prompt 分开保存。

契约不允许以下行为：

- 用历史 prompt 文本猜测用户要引用哪张图。
- 用当前后台默认模型覆盖已开始任务的模型快照。
- 将场景参考图误当成第二个主商品。
- 视觉分析失败后静默降级为无参考图生成。
- 把真实媒体不可读、尺寸或蒙版保护违规当成技术交付成功。
- 把视觉模型报告当作图片事实，或以其失败、不可用撤回已技术交付的图片。

## 图片事实与参考用途

系统保留图片内容事实及其原始置信度，独立解析用户本轮用途。近景图可在 `completeScene=false` 时提供可靠的风格、光线或构图线索；局部线索不能补造完整房间、商品结构或完整摄影事实。商品颜色、材质、结构及关键特征来自明确商品目标或既有商品锚点。

明确请求与稳定引用绑定优先于模型建议。服务端冻结引用别名、资产身份和用途决定，同一决定贯穿计划、编译、独立 QA 与管理员流水；实际供应商图片位置按最终编译顺序映射，不能用附件顺序代替用途。同图可以有多个用途，但每个用途必须有相应事实或可靠线索。

白底商品保护区域计算只消费已解析的准确唯一商品锚点，辅助商品近景即使带有商品事实及核心区域也不参与锚点计数；完整分析和用途绑定保持。已有场景的局部商品保护仍依据当前场景像素与原商品锚点。v6 规划工具与原始输出校验按同一实际来源限制可执行操作：

| 已解析来源               | 操作               | 保护策略           |
| ------------------------ | ------------------ | ------------------ |
| 商品锚点，无当前场景     | `product_to_scene` | `strict_product`   |
| 商品锚点与当前场景       | `local_edit`       | `strict_product`   |
| 当前场景，无独立商品锚点 | `scene_edit`       | `integrated_scene` |

该操作名称只说明执行路径，不增加用户授权。纯风格参考不自动授权新房间或陈设；没有实际场景基线时 `baseline.sceneFacts=null`，本轮增量只来自用户请求与获准线索。无法执行的原始操作或策略返回具体字段问题，沿现有候选与结构修正预算处理，不能静默换操作或放宽商品保护。供应商不支持所需独立蒙版时仍在提交前待复核。

缺少严格商品流程所需的完整商品事实、保护核心或保护范围时，需要补充可靠图片或调整请求，不能靠确认用途继续。当前严格策略不支持的商品改色、材质或结构请求须保留原文并显示具体限制；不能撤销保护、吞掉请求或报告假成功。否定商品属性修改、仅环境属性修改及纯风格引用沿合法环境编辑路径处理。

## 运行架构

首期保持现有 Next.js 单体部署，在同一项目内建立清晰的内部边界：

```text
/create
  ↓
Agent Run
  ↓
图片事实与参考用途解析
  ↓
vision_analysis
  ↓
edit_planning
  ↓
EcommerceEditPlan 校验
  ↓
provider prompt compiler
  ↓
image task executor
  ↓
媒体技术检查
  ↓
登记资产、完成任务、公开结果与内部快照
  ↓（管理员可选开启，后台执行）
视觉参考建议；完成状态与原图片保持
```

逻辑上始终区分 `vision_analysis` 和 `edit_planning`。简单请求可以在物理层合并两次 GPT 调用；商品场景和局部编辑默认使用两阶段，便于验证参考图角色、商品核心和编辑区域。

## 模型路由

模型通过逻辑角色配置，不在业务代码中写死具体模型：

```text
vision_analysis  具备图片输入和结构化输出能力
edit_planning    能理解视觉分析并生成 EditPlan
generation       支持图片生成/编辑和参考图输入
quality_check    可选；比较原始锚点、当前基线和生成结果，只提供视觉建议
```

每个角色允许多个候选模型，按优先级、健康状态和能力匹配选择。故障只在同一角色内切换，不跨角色静默降级。每次任务保存实际使用的模型、策略、编译器和计划版本快照。首次创建冻结 `qualityPolicy=disabled|advisory`，后续恢复沿用该值；无策略的旧任务保持旧恢复语义。关闭时计划的 QA 角色为 `null`，没有 QA 路由或调用，流水记录 `not_run`，不能伪造 `passed`。开启但无可用质检模型时仍交付，报告如实记为不可用。

首期建议默认路由：

```text
vision_analysis  GPT-5.6 或后台配置的同类多模态模型
edit_planning    GPT-5.6 或后台配置的同类结构化规划模型
generation       gpt-image-2.5 主候选，nano banana 2 作为独立候选
quality_check    默认关闭；开启后使用后台配置的可选视觉质检模型
```

## 商品保真策略

### strict_product

默认电商策略，要求可信商品主体 mask。商品核心区强保护，背景和融合光晕区允许生成。无法建立可信 mask 时停止严格流程，不静默降级。

### integrated_scene

允许模型重新融合商品边缘、反射和光影，保留商品身份和主要结构，但不承诺商品核心像素级不变。后续由用户或后台显式选择。

### creative_variation

允许商品外观或构图产生更大变化，用于创意探索，不承诺严格商品保真。

## 工作流

### product_to_scene

输入一张商品主参考图和可选场景参考图。白底背景默认可替换，原有阴影作为姿态和接触面线索，默认重新生成适配新环境的阴影和反射。

商品目标或锚点决定“是什么商品”；辅助图只提供其获准环境、风格、光线或构图线索。明确“参考 A、修改 B”时，A 的可靠线索进入本轮增量，B 的商品事实、画幅与保护范围继续约束执行。

### local_edit

首期只支持背景、环境、场景道具、光线和阴影修改。系统自动定位唯一编辑目标并生成 mask；多个候选目标时只追问一个问题；用户手动编辑区域优先。

商品颜色、材质、结构和包装文字修改进入后续阶段，必须拥有独立的商品核心验收规则。

### scene_edit

用户上传完整家居场景图，输入“柜面加一个花瓶”“去掉右侧摆件”等一句话。系统以该图为场景基线，确定本轮编辑区域和应保护的家具、环境与画幅，再执行局部编辑。没有独立商品锚点时，不得因此绕过电商编排，也不得把家具结构与材质验收全部设为不适用。

## 连续编辑

连续编辑默认以最近已通过技术交付检查、资产 ready 且归属与父链合法的结果作为当前场景基线，不要求视觉 QA `passed`；有原始商品图时永久保留该商品锚点，没有商品锚点的 `scene_edit` 则保留最初场景来源和当前父结果。每轮只记录本轮 `delta`，不无限拼接历史 prompt。

“再生成一张”“重新生成”等简短请求仍继承当前编辑链路；生成出图与技术交付分别判断。已技术交付结果即使有视觉调整建议也可作为默认基线；实际技术失败、未交付或归属/父链不合法的结果不能继承。明确引用历史已交付结果时建立分支，保留实际已有报告，没有报告不补造。

编辑链路继承与执行保护分别验证。简短续写没有授权全局改光、机位或构图时，局部策略仍须确认可信位置后继续原任务；验收不能把“等待确认”误判为未进入编排，也不能换成全局修改指令来规避该保护路径。

用户明确选择历史结果时创建编辑分支，不覆盖其他结果。连续编辑继承当前目标与商品锚点；新场景或风格参考按本轮用途加入，不能自动替换它们。用户明确切换商品或场景目标时，按实际绑定建立相应基线或分支。

## 失败与回退

- 图片事实充分但用途不明确：只提供必要的用途确认，复用同一 Run 的有效分析；不靠模型猜测覆盖明确绑定。
- 商品身份、完整结构或保护范围缺证据：补充可靠图片或调整请求，用途确认不能补造事实。
- 编辑目标有多个候选：只追问一个问题，不扩大 mask。
- 商品 mask 不可信：停止 `strict_product`，给出重新上传或手动标记建议。
- 分析调用失败：按结构输出、传输、鉴权、限流等实际原因分类，沿现有角色路由和候选预算处理；结构修正携带具体字段反馈。分析实际失败可显式消费本轮复核身份重新分析，不能泛称用户图片无效。
- 分析已完成但可靠线索不足：completed 分析的可靠线索不足以形成任何合法用途组合时，也可提供 `retry_analysis`，在原 Run 重新分析冻结输入；缺少商品事实仍须补图，不能通过确认或重试补造。
- 已完成分析后的原件暂时不可读：保留 completed 分析、原分析请求身份和实际路由，在原 Run 提供“重试并继续”；源恢复核同原件 SHA256 后继续，不能降为 failed、清空合法分析或新增分析请求。源核对补修的相关回归与完整门禁按固定证据核验。
- 规划失败：保留原请求，不向图片模型发送未验证的 prompt，不以普通继续绕过参考或保护检查点。
- 原图身份或字节明确变化：保留冻结输入并以 `reference_source_changed` 暂停；重新提供原图，不能在同一资产身份下替换冻结内容。原件读取或父任务校验存储暂时不可用不等于漂移，须按真实原因分类。
- 图片提交前上述暂时故障：从原 Run“检查状态”恢复同一 child；严格核定未提交、零尝试/账单且无提交时间、上游身份或结果后，才允许原子恢复并重新核对原件。失败时零图片 POST、零尝试且不进入 submitting；前台真实接线与相关回归分别核验，不能只提供 API。
- 图片生成失败或连接中断：区分未提交、已提交与提交状态未知；已提交/未知提交只恢复原上游查询，不重新分析、重编计划或重复创建。
- 技术交付检查失败或媒体不可读：保留结果与具体原因，暂停待处理，不公开登记为可用成图。
- 可选视觉质检失败或不可用：已交付结果和完成状态保持，独立记录实际报告并给参考建议；不自动再生成。


## 验收门禁

研发发布使用真实家居商品黄金回归集，并执行自动检查和业务人工复核。它与每轮用户图片的技术交付不同：人工确认真实商品失真仍可否决发布升级或摄影效果比较，但一次模型判断不能拦截用户已经技术交付的成图。

自动检查至少覆盖：

- 输入和结果媒体可读取；
- 商品 mask 覆盖率和编辑区域合法；
- 未编辑区域保护结果可计算；
- 结果资产和父子关系正确保存；
- 实际模型和计划快照完整。

人工检查至少覆盖：

- 商品身份、轮廓、颜色、材质和比例；
- Logo 和包装文字；
- 用户一句话是否完成；
- 欧美家居场景是否自然且适合电商；
- 场景参考图的空间、风格、光线和构图是否被正确借鉴。

研发人工检查发现真实商品核心失真时，不用场景美观度抵消；运行时仅确定性技术失败阻断交付。分析和独立 QA 即使一致也可能共同误判，例如原商品与成图均三层抽屉却都被模型误认四层。用户确认参考用途只确认“用哪张图的哪些线索”，不代表确认结构数量或每条模型事实。

### 执行契约

- 原图事实、参考用途与允许变化分别记录；近景可靠线索不补造完整场景。服务端冻结目标/参考绑定，规划器不得互换 A/B，辅助参考不能借作商品事实答案。
- 可选独立 QA 重新观察目标或商品锚点与实际结果；参考图只参与获准风格/光线比较。模型对身份、结构、材质和视觉范围的判断作为建议保存；实际媒体不可读、画幅或蒙版像素保护违规仍由技术检查拦截。模型声称不可观察与真实解码失败分别记录。
- 规划复用与实际图片提交均核对冻结原图内容；浏览器 WebP 预览不能作为上游参考。提交从本次已校验的原始字节建立临时输入，持久记录仍使用稳定素材身份，不保存参考副本或内联载荷。
- `/create` 本轮存在有效图片输入、明确图片引用或可继承的场景基线时，按管理员启用范围进入图片编辑编排；LLM 只选择编辑方式，不用文本分类误判来绕过编排。纯文生图使用既有路径，本方案不扩展视频、音频或计费。
- 尺寸优先级沿用统一规则：本轮文字明确尺寸 > 当前精确自定义宽高 > 本轮主基线图比例 > 规划尺寸 > 后台默认；“保持原尺寸”属于文字明确约束。场景局部编辑未要求换画幅时，锁定当前基线真实宽高与构图。场景风格参考不得覆盖主基线的画幅。
- `auto` 不等于固定 1:1 或 16:9。记录约束来源、请求尺寸、上游原生文件尺寸和落盘尺寸；真实文件解码结果优先于 LLM 描述。复用已有尺寸检查与规范化能力，不把插值放大说成原生高分辨率，不用裁切、拉伸或补边掩盖失败。
- 局部编辑必须将目标区域转成与主图对齐的独立蒙版，并校验坐标和语义。固定镜头下优先复用已有选区外合成保护；允许变化的边缘和阴影范围需写入计划。构图或视角整体改变属于另一种明确编辑范围，不能按局部保真宣布成功。
- 结构事实包含可见抽屉、柜门、把手、腿脚和视角；不确定事实保留不确定性，不能把规划器的结论当作验收标准答案。场景编辑没有商品锚点时仍检查受保护家具，Logo 等只在确实不可见或无关时设为不适用，并记录原因。
- 生成与可选视觉质检角色独立配置，允许使用相同或不同模型；换模型不改变技术契约。开启的质检需重新观察基线与结果，结合确定性媒体数据和局部证据，不能只复述规划。蒙版支持以真实 provider 协议为准，不能按模型简称推定，能力不足不静默改成整图重绘。
- 真实媒体解码、原生与落盘尺寸、蒙版外像素保护、资产保存和合法归属/父链为技术门禁。技术通过即“已完成”；视觉模型发现身份、结构、材质或构图问题时只显示“参考建议”，服务不可用也不退回或隐藏图片。
- “高级质感”应来自真实纹理方向与尺度、合理粗糙度/光泽、主补光、遮挡及接触阴影、空间层次和留白；不得统一染黄、制造油亮高光、过度锐化，或通过改动商品结构换取场景美观。
- 用户仍只需一张图和一句话。内部分析、计划、蒙版、执行参数和验收证据仅管理员可见；用户看简短状态和明确的后续操作。每轮证据保存在服务端，沿用稳定 Run/任务/结果 ID。

## Task21：局部编辑原生分辨率适配

这是 Task20 真实尺寸失败引出的补修。此前把“原生返回必须等于源图”同时用于合成和技术交付，误拦截了可安全映射的同画幅结果。受控真实请求进一步发现：源图 `3840x2160` 的原生返回为 `1672x941`，整数边长不满足精确比例交叉乘，但符合等比画幅的像素取整；单纯精确同比仍会误退回。最终原画幅和选区外原始像素仍是硬要求，上游原生分辨率作为独立事实保存。

### 尺寸与保护契约

- 原件身份、真实字节摘要、源尺寸、已确认选区和独立 alpha 蒙版保持冻结；提交给上游的原件、蒙版及实际请求尺寸不因结果适配而改变。
- 上游返回可真实解码，且与源图精确同宽高比时，允许把生成像素等比映回源坐标。不同像素尺寸记录 `normalization=uniform_scale`；同尺寸记录 `none`。
- 非精确同比只接受两个边长的四舍五入区间存在共同等比因子：用 BigInt 检查 `2 * abs(nativeW * sourceH - nativeH * sourceW) < sourceW + sourceH`。严格小于排除仅端点接触的空区间，不使用百分比容差或模型尺寸特例。通过后记录 `pixel_grid_scale`，将生成图边界对应到完整源像素栅格；不裁切或补边，也不把该栅格重采样宣称为精确等比矩阵或供应商内部未裁切的证明。区间不相交的画幅继续拒绝。
- 只交付用户允许区域内的生成增量；选区外复制原图对应坐标像素，并重新解码合成结果逐像素检查。最终图保持源图完整宽高，独立保存未缩放的原生返回图、蒙版和最终图。
- 原生实际宽高、最终宽高、实际请求尺寸、适配方式和保护摘要进入内部证据。变化像素数使用源坐标的 `mappedOutsideChangedPixels`；跨分辨率时不填写原生逐像素变化数量，不宣称上游原生输出了最终分辨率。
- 两种适配时，技术交付重新读取真实源图、原生返回、蒙版和最终图，重建合成并核对实际适配模式、尺寸、摘要及选区外像素。`nativeMatches=false` 如实保留，只有独立映射验证成功才接受最终源画幅；普通非局部任务仍执行原生画幅约束。
- 比例错误的安全失败信息记录源宽高与解码后的原生宽高，不包含图片、素材地址、提示词或凭据。所有结果验证后才开始保存；保存中途失败清理本批已写媒体。适配不增加模型调用，不切换模型，不改变未知提交恢复或重试规则。

提交前参考核对故障子任务恢复与用途复核分别处理：补修要求公开 Run 的“检查状态”由服务端派生 `canCheckStatus`，前台以普通 resume 接到原 child 的恢复入口，不暴露 child 内部 ID；服务端校验归属、执行阶段、当前状态和租约，并要求合法且符合原任务契约的 frozen dispatch。recover 与 scheduler CAS 采用同一组提交前恢复准入门禁，`canCheckStatus` 派生复用同一恢复资格。仅已知源读取/父任务校验暂时不可用，且明确未提交、零尝试/账单、无提交时间/上游身份/结果，并同时满足上述全部条件时，才允许同 child 原子恢复至 created，核同冻结原件后提交；任一条件不满足均拒绝该提交前恢复。已有上游、结果或提交状态未知仍只查询或保存原身份，不能重建 child、重发或重新计费。实际前台链路、相关回归和完整门禁分别核验固定证据。已确认选区的蒙版能力复核恢复按 Task20 独立资格处理，不能扩大该参考故障恢复范围。

同批多结果的补修合同候选要求：服务端可恢复 review 项不得被正常 polling/completed 或严格未提交的 created sibling 阻断；正常 sibling 仅继续原任务 GET，不发 recover、不重建，沿原 Run/child/上游身份接续。该执行接线与相关回归证据单列核验，不能将本条合同文稿称为已测试或已发布。

旧已提交/未知提交任务继续原上游，不重新消费用途或重建任务。管理员流水保留分析、归一化审计、用途来源、采用线索、计划、图片位置、结果及独立验收，暂停同样保留已完成证据。

同一上游任务从轮询进入结果落盘时，保留原任务身份和原提交时间；保存阶段使用独立保存时间。已完成任务再次被 Worker 接管应无新增提交、媒体或业务状态变化。暂停任务的页面订阅继续观察原任务，自动恢复不得覆盖已有连接；用户显式确认或重试才按原契约切换订阅。

Worker 无浏览器 Cookie 恢复时，视觉分析、主基线读取和结构化规划均须将已验证的签名上下文转换为内部鉴权头。鉴权回归分别控制匿名拒绝、原上下文误放 Cookie 被拒绝、合法 Worker 头成功及源图字节一致，再验证真实业务函数。测试收集或导入失败不算有效失败证据；偶然一次通过不能关闭未查明原因的间歇失败。

关键缺陷需同时记录有效失败、根因、最小修复、固定源码与修后证据。真实可执行 Worker 重启、数据库/HTTP 回归、页面 DTO 交互、供应商视觉效果及用户人工验收分列；跳过和未执行用例不计入通过。记忆后台提取、私有笔记落盘和服务端入库确认也分别记录，没有回执不宣称入库。

## 非目标与安全边界

- 不用模型名称替代业务能力定义。
- 不让用户承担内部规划和 mask 选择的复杂性。
- 不把未验证的模型能力写成后台可用能力。
- 不把内部计划写入用户公开消息。
- 不在首期为了产出结果而静默降低商品保真策略。
- 不因为连续编辑而覆盖历史结果或丢失原始商品锚点。
